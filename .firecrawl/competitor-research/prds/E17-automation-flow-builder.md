State Machine\n\nEach flow run operates as a state machine. The run tracks the current node and transitions based on node completion.\n\n```\nStates: active → completed | failed | cancelled | paused\n\nNode execution lifecycle:\n  pending → executing → completed | failed | skipped\n  pending → waiting (delay nodes) → executing → completed\n\nTransitions:\n  1. Trigger fires → Create flow_run (status=active) + first run_step (status=pending)\n  2. Executor picks up pending step → status=executing → execute node logic\n  3. On success → status=completed → determine next node(s) via edges → create next run_step(s)\n  4. On delay → status=waiting, scheduled_for=<timestamp> → cron picks up when time arrives\n  5. On condition → evaluate → follow matching edge → create run_step for target node\n  6. On failure → status=failed → retry logic or mark run as failed\n  7. On last node completed with no outgoing edges → mark run as completed\n```\n\n### 4.3 Execution Engine\n\nThe execution engine is responsible for processing flow runs. It operates as a combination of event-driven triggers and scheduled polling.\n\n**Architecture:**\n\n```\n┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐\n│  Event Sources   │────▶│   Flow Matcher   │────▶│  Run Creator    │\n│  - Loan closing  │     │  - Matches event │     │  - Creates run  │\n│  - Survey resp.  │     │    to active     │     │  - Creates first│\n│  - Review sub.   │     │    flow triggers │     │    pending step │\n│  - Webhook       │     │  - Deduplicates  │     │                 │\n│  - Scheduled     │     │  - Rate limits   │     │                 │\n└─────────────────┘     └──────────────────┘     └────────┬────────┘\n                                                           │\n                                                           ▼\n┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐\n│  Action Workers  │◀────│   Step Queue     │◀────│  Step Scheduler │\n│  - Send email    │     │  (Postgres-based │     │  - Picks up     │\n│  - Send SMS      │     │   job queue)     │     │    pending steps│\n│  - Webhook push  │     │  - Priority      │     │  - Picks up     │\n│  - Escalate      │     │  - Retry logic   │     │    waiting steps│\n│  - Update record │     │  - Dead letter   │     │    past due     │\n└────────┬────────┘     └──────────────────┘     └─────────────────┘\n         │\n         ▼\n┌─────────────────┐\n│  Step Completer  │\n│  - Marks step    │\n│    completed     │\n│  - Evaluates     │\n│    next edges    │\n│  - Creates next  │\n│    pending steps │\n│  - Marks run     │\n│    complete if   │\n│    no more nodes │\n└─────────────────┘\n```\n\n**Queue System:**\n\nPhase 1 uses a Postgres-based queue (`automation_flow_run_steps` with status + scheduled_for) polled by a Supabase Edge Function on a 30-second cron. This is sufficient for initial volumes.\n\nPhase 3 migrates to a proper job queue (BullMQ on Redis or Inngest) for higher throughput and better retry semantics.\n\n**Polling Query (Delay Resolution):**\n\n```sql\nSELECT rs.*\nFROM automation_flow_run_steps rs\nJOIN automation_flow_runs r ON r.id = rs.run_id\nWHERE rs.status = 'waiting'\n  AND rs.scheduled_for <= now()\n  AND r.status = 'active'\nORDER BY rs.scheduled_for ASC\nLIMIT 100\nFOR UPDATE SKIP LOCKED;\n```\n\n**Concurrency and Ordering:**\n\n- Each flow run processes one step at a time (no parallel branches in Phase 1; Phase 2 adds parallel paths after condition nodes)\n- Steps are processed in order using the edge graph (topological sort)\n- `FOR UPDATE SKIP LOCKED` prevents double-processing in multi-worker scenarios\n\n**Retry Policy:**\n\n- Action failures retry up to 3 times with exponential backoff (30s, 2min, 10min)\n- After 3 failures, the step is marked `failed` and the run is marked `failed`\n- Failed runs are surfaced in the UI with error details and a \"Retry\" button\n\n**Rate Limiting:**\n\n- Email: 100/minute per organization (aligns with Resend limits)\n- SMS: 30/minute per organization (aligns with Twilio limits)\n- Webhook: 60/minute per endpoint\n- Rate limit enforcement happens in the Step Queue layer\n\n### 4.4 Event System\n\nFlow triggers connect to RepWell events through a publish/subscribe pattern.\n\n**Event Types:**\n\n```typescript\ntype AutomationEvent =\n  | { type: 'loan_closing'; data: { loan_id: string; loan_type: string; borrower_id: string; lo_id: string; branch_id: string; close_date: string; } }\n  | { type: 'survey_response'; data: { survey_id: string; response_id: string; borrower_id: string; nps_score: number; rating: number; template_id: string; } }\n  | { type: 'review_submitted'; data: { review_id: string; source: string; rating: number; borrower_id: string; has_text: boolean; } }\n  | { type: 'webhook_received'; data: { webhook_id: string; payload: Record<string, unknown>; } }\n  | { type: 'scheduled'; data: { schedule_id: string; audience_query: Record<string, unknown>; } }\n  | { type: 'anniversary'; data: { borrower_id: string; anniversary_type: string; loan_id: string; } };\n```\n\n**Event Publishing Points:**\n\nEvents are published from existing RepWell server actions and API routes. Each publishing point calls a shared `publishAutomationEvent()` function that:\n\n1. Validates the event payload with Zod\n2. Queries active flows matching the event type and organization\n3. Mortgage-Specific Adaptations\n\n### 7.1 Loan Closing Triggers\n\nThe primary automation trigger in mortgage is the loan closing event. RepWell's flow builder treats this as a first-class trigger with deep configuration:\n\n- **Loan type segmentation:** Purchase, refinance, cash-out refinance, HELOC, reverse mortgage, VA, FHA, conventional, jumbo. Each loan type may warrant different messaging tone and timing.\n- **Closing date offset:** Configurable delay from closing date (typically 1-5 business days) to allow funding confirmation and initial setup.\n- **Co-borrower handling:** Option to send to primary borrower only, co-borrower only, or both (separate flow runs).\n- **Referral source tracking:** Capture whether the loan came from a realtor referral, online lead, past client referral — available as a condition for customizing messaging.\n\n### 7.2 Loan Officer Assignment\n\nEvery flow run in a mortgage context is associated with a loan officer. This enables:\n\n- **LO-branded communications:** Email templates automatically include the LO's photo, name, NMLS#, direct phone, and email signature.\n- **LO-specific review links:** Google review links point to the LO's Google Business Profile (if they have one) or the branch's profile.\n- **LO notification:** LOs receive real-time notifications when their borrowers respond to surveys, leave reviews, or submit videos.\n- **LO filtering in conditions:** Branch based on which LO originated the loan (e.g., different flows for top producers vs. new LOs).\n- **LO performance tracking:** Flow analytics filterable by LO, feeding into existing leaderboard system.\n\n### 7.3 Branch Segmentation\n\nMulti-branch mortgage companies need branch-level control:\n\n- **Branch-specific flows:** Clone a corporate flow and customize for a branch (local messaging, branch-specific review links, branch manager as escalation target).\n- **Branch-level permissions:** Branch managers can view and manage flows scoped to their branch. Only admins can create organization-wide flows.\n- **Branch filtering in triggers:** Trigger only fires for loans closed by LOs in specific branches.\n- **Branch-specific Twilio numbers:** Different SMS from-numbers per branch for local presence.\n\n### 7.4 Compliance Guardrails\n\nMortgage communications are subject to regulatory scrutiny:\n\n**RESPA Compliance:**\n- No communication can imply that a positive review will result in a benefit (lower rates, fee discounts)\n- Template checker flags RESPA-violating language patterns\n- All review requests must include language that honest feedback is valued regardless of sentiment\n\n**TCPA Compliance:**\n- SMS requires explicit prior consent\n- Consent tracking table (`contact_sms_consent`) with full audit trail\n- Time-of-day restrictions enforced at the engine level\n- Auto-opt-out on \"STOP\" reply with confirmation message\n\n**CAN-SPAM Compliance:**\n- All emails include physical mailing address\n- Unsubscribe link in every email (auto-appended if not present in template)\n- Opt-out honored within 24 hours (immediate in practice)\n\n**State-Specific Rules:**\n- Configurable per-state rules (some states have additional communication restrictions)\n- State determined from contact's property address or mailing address\n\n**Audit Trail:**\n- Every communication sent through a flow is logged with: timestamp, content, recipient, channel, consent status at time of send, compliance checks passed\n- Exportable audit log for regulatory examinations\n- 7-year retention policy for all communication records\n\n### 7.5 Realtor Partner Flows\n\nMortgage professionals often want to strengthen relationships with referring realtors:\n\n- **Realtor notification action:** When a borrower leaves a positive review mentioning their realtor, notify the realtor with a thank-you and the review snippet.\n- **Co-branded review requests:** Include both the LO and the realtor's branding in the review request (configurable).\n- **Realtor referral tracking:** Tag flow runs with the referring realtor for ROI analysis.\n\n---\n\n## 8.
